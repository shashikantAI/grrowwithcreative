6. The full report Claude gave me (unchanged)

Don't launch app.py as-is. It has six flaws that are each exploitable with a single request, most of them without logging in. I reviewed by reading the code only; nothing was run.

Critical

1. SQL injection in login — app.py:29

The username is pasted straight into the query. Logging in as admin' -- with any password skips the password check, and a UNION payload can dump the whole database.

Fix: use a parameterised query, as you already do at line 40:

execute("SELECT id, role FROM users WHERE username = ? AND password = ?", (user, pw))

2. Arbitrary file read in /download — app.py:46

There is no login check, and os.path.join("uploads", name) accepts ../ and absolute paths. /download?file=../shop.db hands over the database, and ?file=../app.py hands over the source and secret key.

Fix: use flask.send_from_directory("uploads", name), which rejects traversal, and require a login.

3. /admin/users has no access control — app.py:48

Anyone on the network can list every user's id, username and email. session["role"] is set at login but never checked anywhere.

Fix: require session.get("role") == "admin", ideally through a shared @login_required / @admin_required decorator.

4. Hardcoded, guessable secret key — app.py:8

Flask sessions are signed with this key. Anyone who knows "supersecret123" (guessable, and readable via finding 2) can forge a cookie with any uid and role and become any user.

Fix: load it from an environment variable holding the output of secrets.token_hex(32), and keep it out of source control.

High

5. Any logged-in user can read any invoice — app.py:40

The query checks that someone is logged in but not that the invoice is theirs, so a user can walk through /invoice/1, /invoice/2, and so on.

Fix: add AND user_id = ? with session["uid"] (adjust to your actual owner column) and return 404 when there is no row.

6. Reflected XSS in /profile/bio — app.py:56

The bio is echoed into HTML unescaped, so <script>…</script> runs in the victim's browser. An attacker's page can auto-submit the form to trigger it, and the script can then act as the victim.

Fix: escape with markupsafe.escape(bio) or render through a Jinja template, which escapes by default.

7. Unsalted MD5 passwords — app.py:27

If the database leaks (see findings 1 and 2), most of these hashes can be cracked in seconds.

Fix: use werkzeug.security.generate_password_hash / check_password_hash: look the user up by username, then verify the hash in Python. Existing users need rehashing at next login or a password reset.

Medium / hardening

  • No CSRF protection on the POST routes. Add Flask-WTF's CSRFProtect and set SESSION_COOKIE_SAMESITE="Lax" explicitly.
  • No rate limiting or lockout on /login, so passwords can be brute-forced. Flask-Limiter covers this.
  • Session cookie settings: set SESSION_COOKIE_SECURE=True once you are on HTTPS, call session.clear() before setting the uid at login, and add a logout route.
  • Deployment: app.run is the development server. Use gunicorn or waitress behind a TLS-terminating reverse proxy.
  • Database connections are never closed — app.py:10. This is a resource leak under load; use a with block or Flask's g plus a teardown handler.

debug=False and binding to 127.0.0.1 are both correct; keep them.

Fix order

Fix 1–4 first, since they need no account to exploit, then 5–7. If the app has ever been reachable by others in this state, rotate the secret key and treat the stored passwords as compromised.
