API Key Leak Checklist — scan, block, revoke (shashikant.ai)

Deleting .env does NOT remove your key. Git keeps every old commit, so anyone with the repo can run git show <old-commit>:.env and read it. Do these 6 steps once, and you are covered.

Tested on gitleaks 8.30.1 (Nov 2026). All keys in this guide are fake.

1. Install gitleaks (free, open source)

  • Windows: winget install --id Gitleaks.Gitleaks -e
  • Mac: brew install gitleaks
  • Linux / no package manager: download from https://github.com/gitleaks/gitleaks/releases (for example gitleaks_8.30.1_linux_x64.tar.gz or gitleaks_8.30.1_windows_x64.zip), unzip, put gitleaks on your PATH.
  • Check: gitleaks version → prints 8.30.1 (or newer).

2. Run the two scans (inside your project folder)

command what it checks catches a deleted .env?
gitleaks dir . only the files on disk right now NO
gitleaks git . every commit in the history YES

What we saw on our test repo (.env committed, then deleted in the next commit): - gitleaks dir . → no leaks found ← this is why people think they are safe - gitleaks git . → leaks found: 2 (one OpenAI key, one Claude key, both in the old commit)

Tip: add -v to see file, line and commit. Add --redact when sharing a screenshot so the key is hidden. Rule: always run gitleaks git . before you push a repo or make it public.

3. Block it before every commit (pre-commit hook)

Create the file .git/hooks/pre-commit (no extension) inside your repo with this content:

#!/bin/sh
# Block the commit if a secret is in the staged changes.
gitleaks git --pre-commit --redact --staged --verbose

Then on Mac/Linux/Git Bash: chmod +x .git/hooks/pre-commit (Windows: Git for Windows runs this file through its own shell; gitleaks just has to be on your PATH.)

Tested: committing a file with a fake OpenAI key → the hook printed RuleID: openai-api-key … leaks found: 1 and the commit was blocked. A normal file → no leaks found, commit went through.

Notes: - .git/hooks is not shared when you push. Every teammate must add it, or use the pre-commit framework: yaml # .pre-commit-config.yaml then run: pre-commit install repos: - repo: https://github.com/gitleaks/gitleaks rev: v8.30.1 hooks: - id: gitleaks - git commit --no-verify skips the hook. Don't.

4. Key already leaked? Do this in order

  1. Revoke the old key first. Delete it in the dashboard:
  2. OpenAI: https://platform.openai.com/api-keys
  3. Claude (Anthropic): https://platform.claude.com/settings/keys
  4. Create a new key, put it only in .env (gitignored) or your host's secret settings.
  5. Check usage/billing for calls you did not make.
  6. Rewriting history is optional. Tools like git filter-repo can remove the old commit, but copies, forks and bots may already have it. Rewriting does NOT make a leaked key safe. Only revoking does.

Wrong order = still hacked: new key + old key still active = the leak is still open.

5. .gitignore lines (add before your first commit)

.env
.env.*
!.env.example
*.pem
*.key
secrets.json

Keep a .env.example with fake values so others know which variables to set: OPENAI_API_KEY=sk-proj-XXXXXXXXXXXXXXXX · ANTHROPIC_API_KEY=sk-ant-XXXXXXXXXXXXXXXX

Note: .gitignore only stops NEW files. If .env was already committed, run git rm --cached .env, commit, and still do step 4.

6. No key at all: Workload Identity Federation (servers + CI)

Your server or GitHub Actions job proves who it is with a short-lived token from its cloud (GitHub, AWS, Google Cloud, Azure/Entra, Kubernetes…), and the AI provider gives back a token that expires in minutes. Nothing to store, nothing to leak.

  • OpenAI WIF (launched 26 May 2026): your workload "uses an identity it already has instead of storing an OpenAI API key." Docs: https://developers.openai.com/api/docs/guides/workload-identity-federation

  • Claude API WIF: short-lived OIDC tokens instead of sk-ant-... keys; set up in Console → Settings → Workload identity ("Connect workload"). Docs: https://platform.claude.com/docs/en/manage-claude/workload-identity-federation

  • Claude Code GitHub Action: anthropics/claude-code-action has the input anthropic_federation_rule_id. It swaps the workflow's GitHub OIDC token for a Claude token, so no ANTHROPIC_API_KEY secret is needed. The job needs permissions: id-token: write.

The honest catch: this is for servers and CI pipelines. On your own laptop you still use a normal key, so steps 1–5 still matter. And if ANTHROPIC_API_KEY is still set where WIF runs, the SDK uses the key instead — remove the old key from CI secrets after switching.
