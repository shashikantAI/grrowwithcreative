Loop Engineering: the playbook

You commented LOOP, so here it is. What loop engineering actually is, the five pieces you build a loop from, and a first loop you can set up tonight. No fluff.

"You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

Peter Steinberger, creator of OpenClaw

"I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops."

Boris Cherny, head of Claude Code

Part 1

The idea (3 minutes)

Prompting vs looping

Prompt engineeringLoop engineering
You writethe one best instructionthe system that keeps instructing
Who checksyou, every timea separate checker agent, then you
When it runswhen you are at the keyboardon a schedule, until the goal is met
Your jobtypingdesigning, reviewing, deciding

IBM's definition: "Loop engineering is the practice of designing agentic workflows, or loops, that iteratively guide AI agents toward completing user-defined goals with minimal human intervention."

The loop itself: four stages

01GoalOne specific, testable target with a clear stop condition.
02ActionThe agent does one thing: writes code, runs tests, fixes a bug.
03ObserveThe system checks what happened. Did CI pass?
04AdjustFeedback goes back in. The loop starts again.

Good goal: "all tests in test/auth pass and lint is clean". Bad goal: "improve auth".

A goal without a stop condition is just a bill.

What each one buys you

  • Automations. Runs that find something land in a triage inbox. Runs that find nothing archive themselves. You only look when there is something to look at.
  • Worktrees. "One agent's edits literally cannot touch the other one's checkout." They fix file collisions. They do not fix your bandwidth: your review capacity is still the ceiling.
  • Skills. Without them the loop "rederives your whole project from zero every cycle". With them, you explain your project once.
  • Connectors. The difference between an agent that says "here is the fix" and a loop that opens the PR, links the ticket, and pings the channel once CI is green.
  • Subagents. "The model that wrote the code is way too nice grading its own homework." A second agent, with fresh context, does the grading. Costs more tokens. Spend them where verification matters.
  • State. A loop with no memory repeats its own mistakes. One markdown file fixes that.

Part 3

Build your first loop tonight

The example uses Claude Code. The same shape works in the Codex app with the equivalents from the table above.

Pick a boring job first.

Flaky tests, lint errors, dependency bumps, stale TODOs. Something with a yes/no finish line.

  1. Write the goal with a stop condition

    GOAL: every test in test/auth passes and lint is clean.
STOP when: both are true, OR 5 attempts are used, OR the same error shows up twice.
NEVER: touch files outside src/auth and test/auth. Never push to main.

    Three parts, always: done condition, give-up condition, off-limits list.

  2. Write the skill (project knowledge, once)

    .claude/skills/fix-tests/SKILL.md 
    ---
name: fix-tests
description: How to run, read and fix failing tests in this repo. Use whenever tests fail.
---

- Run tests with: npm test -- --runInBand
- Lint with: npm run lint
- Auth code lives in src/auth. Fixtures live in test/fixtures. Do not edit fixtures.
- Fix the code, not the test, unless the test itself is provably wrong. Say why.
- One fix per attempt. Re-run the tests after every change.
- Append one line to PROGRESS.md after every attempt: what you tried, what happened.

  3. Write the checker (the maker never grades itself)

    .claude/agents/checker.md 
    ---
name: checker
description: Verifies a change after the maker finishes. Use after every fix attempt.
tools: Read, Grep, Glob, Bash
---

You did not write this code. Do not trust the maker's summary.

1. Run the tests and the linter yourself. Paste the real output.
2. Read the diff. Flag: deleted or skipped tests, weakened assertions,
   hard-coded expected values, edits outside src/auth and test/auth.
3. Answer PASS or FAIL on the first line, then the reasons.

You cannot edit files. You only report.

    Read-only tools on purpose. A checker that can edit becomes a second maker.

  4. Add the state file

    PROGRESS.md 
    # Goal: test/auth green + lint clean
## Attempts
- (the loop appends here: attempt number, what changed, result)
## Known dead ends
- (things that were tried and did not work, so they are not tried again)

  5. Isolate it

    git worktree add ../myapp-loop -b loop/fix-auth-tests
cd ../myapp-loop

    The loop works in its own checkout on its own branch. Your main checkout stays untouched while it runs.

  6. Run it by hand once

    Open Claude Code in the worktree and give it the goal from step 1, plus: "Use the fix-tests skill. After each attempt, have the checker subagent verify. Log to PROGRESS.md."

    Watch the whole first run. You are not checking the code yet. You are checking the loop: did it stop when it should, did the checker actually run the tests, did the log get written?

  7. Put it on a heartbeat

    Only after a clean manual run.

    • Inside a session: /loop with an interval re-runs a prompt on a cadence.
    • Unattended: a cron job or a GitHub Actions schedule that runs Claude Code headless (claude -p "...") in the worktree.
    • In the Codex app: the Automations tab, with a cadence and the Triage inbox.

    Start with a slow cadence. Once a night is plenty for a first loop.

  8. Review like an engineer

    Every morning: read PROGRESS.md, read the diff, merge or reject. The loop opens the PR. You still own the merge button.

Part 4

The money rule

"it's still early; I'm skeptical, and you absolutely have to be careful about token costs."

Addy Osmani, in the same essay

A loop that runs while you sleep, spends while you sleep. So:

  • Cap the attempts. Every goal carries a give-up condition (step 1).
  • Cap the spend. Set a monthly usage limit in your provider's console before the first unattended run.
  • Slow the cadence. Nightly before hourly. Hourly before "every 5 minutes".
  • Exit early on nothing. If discovery finds no work, the run should end in one step.
  • Use the checker where it counts. Subagents burn extra tokens, each one does its own model and tool work. Use them on code that ships, skip them on throwaway work.
  • Check the bill after night one, not after month one.

Part 5

Three ways loops go wrong

All three are named in the essay and echoed by IBM

  • Unattended mistakes. "A loop running unattended is also a loop making mistakes unattended." Verification stays your job.
  • Comprehension debt. "The faster the loop ships code you did not write, the bigger the gap between what exists and what you actually get." Stop reading the diffs and you stop understanding your own codebase.
  • Cognitive surrender. "When the loop runs itself, it's very tempting to stop having an opinion." The loop amplifies whoever built it. "The loop doesn't know the difference. You do."

The honest footnote: direct prompting still works. Not everything needs a loop. Loop the repeatable, prompt the one-off.

Part 6

Five starter loops

LoopGoal / stop conditionCadence
Test fixerfailing tests in one folder go green, max 5 attemptsnightly
Lint + type cleanerzero lint and type errors in one packagenightly
Dependency bumperone minor bump per run, tests still green, PR openedweekly
Bug triagernew issues labelled, duplicates linked, repro steps requestedevery few hours
Docs drift checkerREADME commands actually run; open a PR when they don'tweekly

Same rule for all five: small scope, testable finish line, checker before PR, human before merge.

One-page checklist

  • Goal has a done condition, a give-up condition, an off-limits list
  • Project knowledge lives in a SKILL.md, not in your head
  • Checker is a separate agent with read-only tools
  • State file exists and the loop appends to it
  • Loop runs in its own worktree and branch
  • One full manual run watched start to finish
  • Spend limit set before the first unattended run
  • A human reads the diff and owns the merge

"Build the loop. But build it like someone who intends to stay the engineer, not just the person who presses go."
